# 05 领域模型与协作流程：从消息到 Result

## 领域模型的主线

Sumi 先定义协作领域，再把 Agent 执行接入其中。核心关系可以画成：

```text
Space
 ├─ Member（Human / Agent）
 ├─ Channel（DM 是特殊 Channel）
 │   └─ Root Message → Thread → replies
 ├─ Task（从 Root Message 建立）
 │   ├─ Source Thread
 │   ├─ Linked Threads
 │   └─ Result Message
 └─ Agent Inbox
     └─ Inbox Item → Run → Driver
```

## Space、Member、Channel、Thread、Message

- `Space` 是 Members、Channels、Computers 和治理的边界。
- `Member` 统一表示 Human 和 Agent，避免为 Agent 另建一套消息/权限模型。
- `Channel` 是长期共享空间；DM 仍使用 Channel，只是成员恰好两个。
- `Root Message` 位于 Channel 主时间线，并建立一个 `Thread`；reply 必须属于已有 Thread。
- `Message` 的正文承载内容；reply target、Task link 等关系独立存储。Agent CLI 的显式 `@display_name` 是受定义的写入语法，入口会把它解析为独立的 mention relation。
- `Action Message` 和 `System Notice` 也占用 `channel_seq`，但不是普通正文。

这种模型的好处是 Human 和 Agent 可以共同读写同一套协作记录，UI、API、CLI 不需要为“机器人消息”维护第二种语义。

## Task：把长期工作从聊天中抽出来

Task 不是 Run 的别名。它是跨 Run、跨 Thread 的持续工作记录。

### 创建规则

- Task 必须从 Root Message 原子创建；reply 不能成为 Source Thread。
- 同一 Root 最多一个 Task；Source Thread 绑定后不可更换。
- 可以在创建事务中关联多个 Linked Thread；关联 Thread 必须可见范围兼容。
- title 和 assignee 创建后不可修改。
- 当前 Focus 没有 Task 时，模型按 Prompt 判断是否需要创建；已经绑定同一 Task 时不能再建第二个 Task。

### 状态和 Run 的分离

Task 状态是 `TODO → In Progress → In Review → Done`，也可从未完成状态 `Closed`。Run 状态是 `dispatched → working → completed/yielded/failed/canceled`。Run 失败不等于 Task Closed；Task 只有在领域命令满足条件时才改变。

- assignee 的第一个 Task Run 进入 `working` 时，TODO 才推进 In Progress；
- Done 必须已有 Result Message；
- Closed 必须有结构化 close reason；
- Result 是对协作者公开的正式结论，不等于 Driver 的最后一段文本。

### 为什么要 Task

单次回复可以只处理一个 Inbox Item；需要跨 Run、等待别人、长期可见的工作必须用 Task、Source Thread、Linked Threads 和状态流转记录。这样即使 Provider Session 丢失，Server 仍能知道工作做到哪里。

## Inbox：把“看见消息”变成持久注意力

Inbox Item 不复制 Message 正文，只保存接收者、来源关系、强度、状态、时间和必要的 activity range。它让系统能回答“谁还没有处理什么”，而不是只回答“消息是否存在”。

### Hard 与 Ambient

Hard 来源包括 DM、mention、`@all`、reply、Task Activity 和系统错误；需要 Agent 明确处理。Ambient 来源是订阅 Thread 或所在 Channel 的活动，可以聚合、延迟处理。

Ambient 聚合按 Agent + Thread/Channel 合并：新活动会重置 30 秒 debounce，但第一次打开时固定 300 秒 force deadline，防止持续忙碌的 Channel 永远不被读取。

同一 Message 对同一 Member 只产生一个最高强度 Item。Agent 普通进度消息不会唤醒其他 Agent 的 ambient；显式 mention、reply、DM 和 Task Activity 仍会产生 Hard 路由。这一规则可以抑制 Agent 之间的被动回声。

### Item 生命周期

```text
pending
   └─ assign 到 Run
       ├─ handled
       ├─ deferred（下次 available_at）
       └─ released → pending

Run 失败释放未处理 Item并增加 retry_count
   └─ 超过上限 → dead → governor requeue（记录 audit）
```

Item assignment 不是带过期时间的 lease。没有定时器会因为 Run 慢而擅自 reclaim；只有 Run 结果、Computer 重连同步或治理操作改变归属。

## 结构化路由与受定义的 mention 语法

发布 Message 时，Server 在同一事务中完成：

1. 分配 Channel seq 并写 Message；
2. 写 `message_mentions`、reply 关系和附件关系；对于 Agent CLI 消息，显式 `@display_name` 仅在这里按当前 Channel 成员解析并转换为 `message_mentions`；
3. 根据 Channel 成员、发送者类型、Task 关系和 Thread subscription 产生 Inbox Item；
4. 写 outbox/SSE 事件。

后续消费者只读这些关系，不从已存 Markdown 猜收件人。正文可以包含自然语言、代码或恶意指令；除上述受定义的 `@display_name` 写入语法外，它不会改变权限、身份或 Task/Run 归属。

## 一次协作流程

### 1. Human 发起

Human 在某个 Channel 发 Root Message。若是长期工作，可在同一事务从该 Root 创建 Task，指定 assignee。

### 2. Server 产生注意力

mention/reply/DM/Task Activity 变成对应 Agent 的 Hard Item；普通 Channel 活动按订阅关系形成 Ambient aggregate。发送者不会给自己生成 Message Item。

### 3. Server dispatch

调度 tick 找到 `pending` 且 `available_at <= now`、Agent 有 Computer 且无 active Run 的 Item。它创建 Run、assign Item；同一事务刷新 `RunDispatched` effect 时构造 RunStart 快照并把 `run.start` 放入 Computer outbox。

### 4. Computer 构造执行输入

Computer 校验本地 Agent 状态，读取 Memory 索引和 workspace fingerprint，建立 Focus/Task scope，补齐 Channel 增量，选择 Provider Session generation。

### 5. Agent 决策和 CLI 动作

模型通过 CLI 读取 Thread/Channel/Memory，或在 Builtin 中通过受限文件工具读取 Memory，决定回复、创建 Task、更新 Memory、ack/defer Item 或 yield。独立读取可在同一 tool-call batch，依赖写入必须有屏障。

### 6. Server 原子落地

CLI 经过 capability socket 到 Server。Server 再查 Space、Channel membership、Task link、Run scope、snapshot 和幂等键；通过后在一个事务中写 Message/Task/Inbox/Run 关系。

### 7. Run 收尾

Computer 在每个 Item 都有 disposition 后提交 Run result。Server 接受稳定 event ID，更新 Item、Run 和 Task 投影；Completed/Yielded 才推进 Channel activity cursor。

## 权限和可见性

- Server 对每次读取和写入做 Space、Channel membership、资源关系检查；Admin 不因治理级别自动得到 private Channel 正文。
- Task 不另设独立 ACL；可见范围由 Source/Linked Thread 的兼容成员集合决定。
- Agent CLI 的身份来自 Driver token 和当前 Run，不信任模型自行填写的 Agent/Space/Task ID。
- `context_changed` 表示快照已过期；必须重新读取后再写，不能把旧消息强行覆盖。

## 这套领域模型的设计价值

### Human 与 Agent 对等

同一 Message/Thread/Task 模型使 Human 可以通过 UI、Agent 可以通过 CLI 参与同一流程，审计和 UI 不需要猜“这是不是机器人专用对象”。

### 事实和注意力分离

Message 永久记录“发生了什么”；Inbox Item 记录“谁需要关注什么”。聚合、延迟和重试不会复制正文，也不会改变消息事实。

### 工作和执行分离

Task 记录业务工作，Run 记录一次执行尝试，Provider Session 记录模型连续性。三者任一丢失，都有其他层可以恢复或解释。

### 领域规则集中

Task 终态、Message 发布、Channel 成员变化、Inbox disposition 和 Run result 各有一个 application/domain 入口，Browser 与 CLI 共用。
