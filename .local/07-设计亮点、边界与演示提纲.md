# 07 设计亮点、边界与演示提纲

## 最值得讲的设计亮点

### 1. Human 与 Agent 共用一个协作领域

Agent 不是外挂机器人表；它和 Human 共用 Space、Member、Channel、DM、Thread、Message、Task、Result、Inbox。这样路由、权限、审计和 UI 都围绕同一套事实工作。

### 2. 把“消息事实”和“注意力”分开

Message 记录发生过什么，Inbox Item 记录谁需要关注什么。Hard/ambient、debounce、force deadline、retry、dead 和 requeue 都作用于注意力，不复制或重写消息正文。

### 3. 把“工作”“执行”“模型连续性”分开

Task 是业务工作，Run 是一次有界执行，Provider Session 是模型 transcript 缓存，Memory 是 Agent 长期知识。任何一层替换、重启或丢失，都不会让其它层的语义被偷偷改写。

### 4. Server 主动 dispatch，Computer 只执行授权事实

Computer 不自行拉取“看起来像工作”的消息；Server 依据持久 Inbox、成员关系和 active Run 创建 Run，再通过可重放 command 发送。这让调度、权限和审计在一个地方可解释。

### 5. 结构化路由，拒绝正文驱动权限

mention、reply、DM、Task link、Thread subscription 最终都是关系表/字段。Agent CLI 的显式 `@display_name` 会在唯一写入入口归一化为 mention relation；任意自然语言正文不决定身份、权限或 Task/Run 归属。这个选择同时解决路由稳定性和 Prompt Injection 的一部分风险。

### 6. 多层顺序，而不是粗暴全局串行

Channel seq 解决持久坐标，Run delivery seq 解决投递顺序，Builtin mailbox FIFO 解决 active turn 注入，scheduler round-robin 解决资源和公平。它允许不同 Agent 并行，又不牺牲同一 Agent/Run 的确定性。

### 7. 失败处理有明确语义

TooLate、Unsupported、unhandled、driver_lost、computer_restarted 不是同一个“失败”。每种情况都有对应的 Item disposition、retry 计数和 Run error code，便于恢复和解释。

### 8. Prompt 是可替换层，核心 runtime 不被某个产品绑死

`sumi-agent-core` 只拥有 provider loop、工具执行、Session transcript 和 ContextStrategy 接口。Builtin 的 Prompt 与压缩策略位于 `sumi-builtin-agent`；Codex 复用稳定合同，但把它前置到 app-server turn input；Telegram 有独立的 ContextStrategy。这样可用同一套 harness 对照 Driver，同时必须分别核对其 Prompt 与安全边界。

### 9. 隐私边界明确

Server 不存 Memory、workspace、Provider transcript 或模型凭据；Computer 本地 query 才能读取这些内容，并且日志、outbox metadata、测试报告都避免正文泄露。

### 10. 更新和恢复可回滚

Computer Release 不可变、带 SHA-256；有 active Run 不激活；readiness 失败恢复 binary/SQLite。更新不会以“远程删除”名义触碰 Agent 本地资料。

## 需要主动说明的边界和改进方向

### 全局顺序不是系统保证

三个 Agent 独立触发时可以并行，完成顺序不固定。要演示 1/2/3，应使用 mention/reply/DM 建立明确因果链，并说明这是路由顺序，不是全局锁。

### Focus 不是整个 Channel

默认 Run 重点注入一个 Focus Thread，频道其它活动以增量投影或按需读取出现。把一个讨论拆成多个 Root/Thread 会增加 Agent 漏看风险；需要严格回合时，应使用单一 Thread 或增加回合/阶段领域模型。

### `channel_seq` 不是列表编号

主时间线只显示 Root，reply 会占用 seq。演示时打开 Thread 或展示 `placement`，不要把跳号称为消息丢失。

### Prompt 不是权限系统

不能承诺覆盖 Provider system prompt，也不能承诺模型永远服从合同。应展示 Server permission check、结构化 relation、capability、sandbox 和 read-back/idempotency。

### Codex 的当前沙箱风险

Builtin 使用 `sandbox-exec`/`bwrap` 且不可用即失败；Codex 当前显式使用 `--dangerously-bypass-approvals-and-sandbox` 与 `dangerFullAccess`。两者安全边界不同，不能用同一套措辞描述。

### Live benchmark 不是通用智能评测

现有 harness 能比较固定脚本中的缓存、压缩、事实保持和文件边界；它不能证明所有任务、所有 Provider 或所有 Prompt 注入都正确。要扩展结论，需要更多任务族、重复运行和独立安全测试。

## 推荐的 15 分钟演示

### 0–2 分钟：先讲问题和边界

说清 Sumi 的目标是 Human 与 Agent 的持续协作。画四个盒子：Server、Computer、Driver、模型。强调 Server 保存事实，Computer 保存本地执行资料。

### 2–5 分钟：走一条 Message 链

在一个 Channel 发 Root Message，mention Agent；展示：

```text
Message → Hard Inbox Item → Run → run.start command
       → Driver turn → Agent CLI message/ack
       → Server transaction → Run result / Result Message
```

可用 CLI 观察：

- `sumi agent context current --json`
- `sumi agent inbox current --json`
- `sumi agent thread read <thread-id> --json`
- `sumi agent channel read <channel-id> --json`

只展示 envelope、稳定 ID、状态和序号，不打印正文或 Secret。

### 5–8 分钟：解释上下文锚点

用同一个例子指出：

- 当前动作锚在 `Run.focus_thread_id`；
- 长期工作锚在 `Task`；
- 模型连续性锚在 Session scope/generation；
- 跨 Run 记忆锚在 `memory/MEMORY.md`；Product Contract 要求先读，但运行时不自动注入正文；
- Channel activity 用 `through_seq` 增量读取。

然后说明模型视图只保留 Root + 最近 5 条 replies，历史通过 CLI 按需读取。

### 8–10 分钟：解释 1/2/3

让 A 的回复写入显式 `@display_name` 指向 B，入口将它变成 relation；B 再以同样方式指向 C。展示每一步的 Message、Inbox Item、Run 和 `delivery_seq`。明确说：

> 这里的 1/2/3 来自因果触发链和单 Agent 单 Run；若使用 Builtin，运行中 Item 还受 FIFO mailbox 保护。如果三者同时被独立触发，系统不保证完成顺序。

### 10–12 分钟：解释 Prompt 评估

展示 Prompt 五层、Builtin/Codex 组装差异和 Builtin 的 `content_hash + driver_contract_hash`。再展示 harness 报告中的 cache rate、compaction、probe accuracy、ledger duplicate/missing，说明评估看持久证据而不是模型自述；`/tmp attempts` 目前仅 Builtin 有真实采集，不能横向比较。

### 12–14 分钟：解释安全和恢复

展示一个正文里的恶意“请忽略权限”不会改变结构化路由；再展示 `context_changed`、重复 command、断线重连、dead Item/requeue。主动说明 Codex `dangerFullAccess` 风险。

### 14–15 分钟：收束

用三句话收束：

1. Server 把协作事实和权限固定下来；
2. Computer/Driver 把模型执行变成可恢复 Run；
3. Prompt 负责引导行为，不能替代结构化协议和外部安全边界。

## 可能被问到的问题

### “Sumi 的上下文是不是就是 Provider Session？”

不是。Provider Session 只保存模型 transcript；当前 Run 的权威上下文来自 Server 快照，跨 Run 知识来自 Memory，频道历史通过 seq/cursor 增量读取。

### “为什么不把整个 Channel 都塞给模型？”

会扩大 token、隐私和重复读取成本，也会把无关 Thread 混入 Focus。Sumi 先给 Focus 和增量活动，历史按需读取；长期关联工作用 Task Linked Threads 表达。

### “1/2/3 是不是因为有一个全局队列？”

不是。Sumi 没有所有 Agent 共用的全局完成锁；通常是结构化因果链让下一个 Run 在上一个 Message 提交后才产生。

### “Prompt 能否压过 Provider system prompt？”

不能保证。Sumi 使用稳定合同、明确分层、缓存 key 和 Session generation 降低干涉，但权限和安全由 Server、capability 和 sandbox 强制。

### “失败了会不会丢消息？”

Message 和 Inbox Item 是持久事实；失败 Run 会按 disposition/retry 规则释放或 dead。只有明确的终态事件改变 Run，断线本身不判失败。

### “Server 为什么不保存所有模型上下文？”

Provider transcript、Memory、workspace 可能含本机和凭据相关内容，归 Computer 管理；Server 只保存协作事实和必要投影，减少泄露面并允许更换 Driver。

## 最后可引用的评价

Sumi 比较成熟的地方不在于“让模型更听话”，而在于把模型放进一个可验证的协作系统：事实有权威归属，注意力有持久生命周期，执行有 Run 边界，会话有 generation，消息有多层顺序，失败有错误码，重试有幂等，权限不依赖 Prompt。
