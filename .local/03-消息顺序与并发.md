# 03 消息顺序与并发：为什么会出现 1/2/3

## 结论

Sumi 同时维护三种顺序。回答“三个 Agent 能按 1/2/3 返回”的关键不是“系统把所有 Agent 全局串行化”，而是：**结构化因果链把下一个 Agent 的触发放在上一个 Agent 的提交之后；每个 Agent 自己又有单活跃 Run 和连续 delivery 序号，Builtin 在运行中的 turn 还用 FIFO mailbox 接收新 Item。**

如果三个 Agent 是独立同时触发的，系统不保证它们按编号完成。

## 三种主要顺序

| 层级 | 坐标 | 实现 | 能保证的范围 |
| --- | --- | --- | --- |
| Channel 消息 | `channel_seq` | Channel 行上的 `next_seq` 原子递增；`UNIQUE(channel_id, channel_seq)` | 同一 Channel 的 Root、reply、Action Message、System Notice 有统一持久坐标。 |
| Run 投递 | `delivery_seq` | 正常创建/attach 路径按 1、2、3… 分配；`run_items` 只做唯一约束；Computer 复原严格校验连续性 | 同一 Run 的本地投递按连续坐标处理；Server 持久层独立拒绝重复和 0，但当前不独立拒绝缺号。 |
| Builtin turn 输入 | `TurnMailbox` 的 `VecDeque` | 入队与关闭在同一 mutex 中判断；turn 结束后 FIFO drain | 同一 Builtin turn 里的 steer/notice continuation 按入队顺序执行。 |

还存在一层控制通道顺序：每台 Computer 的 command 有稳定 `command_id` 和递增 `computer_seq`，用于命令落盘、重放和幂等；它不等于 Agent 回复顺序。

## `channel_seq` 为什么会跳号

`channel_seq` 是 Channel 内全部 Message 共用的坐标，但主时间线只展示 `placement='root'` 的消息；Thread pane 才展示 Root 及 replies。因此主列表出现 `1、3、7` 并不表示丢消息，中间的序号可能是 reply 或不在当前列表位置的 Action Message。System Notice 本身是 `placement='root'` 的系统行，UI 可折叠连续 Notice，但它并没有从主时间线消失。

正确的讲法是：

- `channel_seq` 适合做稳定引用和快照边界；
- 它不是当前 UI 列表的行号，也不是“第几轮发言”；
- 要看完整因果关系，应打开 Thread 或使用 `thread.read`/`channel.read`。

数据库以 `UPDATE channels SET next_seq=next_seq+1 RETURNING next_seq-1` 在事务中分配序号。Agent CLI 消息中的显式 `@display_name` 也在此唯一写入入口转换为结构化 mention；后续路由只读 relation。

## 三个 Agent 报数的因果链

假设测试不是让 A、B、C 同时独立回答，而是要求“收到上一个 Agent 的消息后再报下一个数”：

```text
Human / 外部触发
       │
       ▼
Agent A 的 Run
       │ 发送含显式 `@display_name` 或 reply 的“1”
       │ 事务提交 Message + B 的 Hard Item
       ▼
Server dispatch B 的 Run
       │ B 处理 delivery_seq，发送“2”
       │ 事务提交 Message + C 的 Hard Item
       ▼
Server dispatch C 的 Run
       │ C 发送“3”
```

这里的顺序来自四个事实：

1. A 的显式 `@display_name` 在写入入口转换为 `message_mentions`，或由 reply/DM 建立现成关系；发布事务同时提交 A 的 Message 和 B 的 structured attention。B 不会因 A 尚未提交的消息被触发。
2. 一个 Agent 同时最多一个 active Run，Server partial unique index 和 Computer 本地 scheduler 都会挡住同 Agent 的并发 Run。
3. B/C 的 Hard Item 按 `delivery_seq` 进入对应 Run；重复命令或重复 delivery receipt 按稳定 ID 幂等。
4. B 的回复再次经过 Server 事务，才产生 C 的 Item。没有这条结构化因果链时，三个 Run 可并行。

Prompt 里的“报 1、2、3”只影响模型选择的数字；系统保证的是触发和持久化顺序，不保证模型不会算错、重复报数或拒绝调用 CLI。

## Server 如何选择并发工作

Server 的 `dispatchable_work` 每次对每个 Agent 最多选一个可用 Item，过滤 active Run、成员可见性和 `available_at`。Computer 收到后由本地 Scheduler 处理：

- 总容量由 `max_concurrent_runs` 限制；
- 每个 Agent 只有一个 active slot；
- Agent 间使用 round-robin；
- Agent 自己的队列代码支持显式 Human redirect、Hard/Ambient、available time、Task continuity 的优先级；当前 `RunStart` 固定把 `explicit_human_redirect` 写为 `false`，实际生效的是 Hard、available time 与 Task continuity。

这解决公平性和资源上限，不建立跨 Agent 的全局完成顺序。

## Run 内的新消息如何保持顺序

Server 发现 active Run 与新 Hard Item 的 scope 一致时，追加下一个 `delivery_seq`，再发送 `run.attach_item`。Computer 的流程是：

1. 本地事务先把 Item 放进连续序列；
2. Driver 返回 `Accepted`、`TooLate` 或 `Unsupported`；
3. Computer 记录 delivery receipt 和 Item disposition；
4. Server 以稳定 event ID 幂等地确认结果。

Builtin Driver 把 Accepted Item 放入 `TurnMailbox`。主 provider turn 完成后，运行时在 mailbox 关闭屏障前反复取出 FIFO 批次，按批次建立 continuation turn；同一批里也保持入队顺序。入队与“空队列后关闭”竞争时，先拿到锁的操作决定归属：已接受的 Item 必须进入当前 Run，关闭后才到达的 Item 返回 `TooLate`。

Codex Driver 使用 app-server 的 `turn/steer`；接受与否由 app-server 返回，失败时记录 `TooLate` 或传输错误。不同 Driver 的内部实现不同，Server 只依赖统一的 outcome 协议。

## 终态和并发竞争

- Attach 与 Run finalization 同时发生时，Computer 第二次事务重新读取当前 Run；如果终态已赢得竞争，delivery 变成 `TooLate` 并释放 Item，不用旧快照覆盖终态。
- Accepted Item 如果直到 Run 完成仍无 disposition，Run 以 `unhandled_items` 失败；不能静默完成。
- TooLate/Unsupported 会被释放，不污染原 Run 的失败状态。
- `run_items` 的 `(run_id, delivery_seq)`、Item ID、delivery event ID 都有唯一约束，重复结果不会重复计数。
- `run yield` 是该 Run 最后一个 CLI 调用；后续工作由新的 Run/continuation note 接手。

## 能保证什么

- 同一 Channel 的持久消息坐标不会因为 UI 只显示 Root 而改变。
- Computer 本地 `LocalRun` 拒绝缺号、重复或 scope 错配的投递；正常 Server 路径也顺序分配 `delivery_seq`。
- 同一 Builtin turn 中，已 Accepted 的 mailbox 输入不会在“模型刚完成”时被丢掉。
- 同一 Agent 不会因两个 active Run 互相覆盖 Provider Session 或 Inbox disposition。

## 不能保证什么

- 不保证多个独立 Agent 的全局完成顺序、网络到达顺序或模型输出顺序。
- 不保证 Server 数据库单独检查 `delivery_seq` 没有缺号；它目前只检查正数和不重复，连续性由正常分配路径与 Computer 本地校验维持。
- 不保证 `channel_seq` 连续显示在主时间线；reply 和系统消息会占用序号。
- 不保证模型遵守报数、轮流发言或不重复回复；这些需要结构化路由、持久证据和场景测试共同验收。
- 不保证旧 Driver 的 steer 能力与 Builtin 相同；能力差异必须看 delivery outcome，而不是猜测。

## 对“狼人杀错过轮次”历史问题的正确表述

[`docs/problems/2026-08-09-werewolf-seq-missed-turns.md`](../docs/problems/2026-08-09-werewolf-seq-missed-turns.md) 记录的是较早 commit 的问题：当时 Builtin 不支持运行中 steer，未处理 Item 的失败路径也没有错误码。当前代码已经加入 mailbox、`unhandled_items`、delivery outcome 和竞态补偿；这份历史文档仍可用来说明为什么要有这些不变量，但不能作为当前行为的描述。

历史问题仍暴露两个产品边界：同一讨论若散落多个 Thread，Focus 不会自动变成整个 Channel；多人轮转若需要严格回合，应增加结构化回合模型或明确使用单一 Thread。
