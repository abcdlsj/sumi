# 02 上下文与会话：锚点、快照和连续性

## 先回答“锚点是什么”

Sumi 没有一个包打天下的“全局上下文”。不同问题使用不同锚点：

| 问题 | 权威锚点 | 作用 |
| --- | --- | --- |
| 当前 Run 正在处理什么 | `Run.focus_thread_id` | 决定本次执行的主 Thread、可见 Channel 和写入范围。 |
| 一项长期工作属于哪里 | `Task` + `Source Thread` + `Linked Threads` | 跨 Run 追踪同一工作；Source Thread 创建后不可更换。 |
| 消息读到哪里 | `channel_seq`、`message_snapshot_sequence`、`channel_snapshot_sequence` | 组成一次一致的读取边界。 |
| 模型如何保持对话连续 | `(Agent, SessionScope, generation)` 的 Provider Session | 复用本地 transcript；不承载 Server 正式状态。 |
| Agent 跨 Run 记住什么 | `Agent ID` 对应 Agent Home 的 `memory/MEMORY.md` 和 `notes/` | 保存可恢复知识；不复制完整消息历史。 |

因此，回答“上下文基于什么”时，最准确的说法是：**执行以 Focus Thread 为锚，长期工作以 Task 为锚，模型连续性以 Provider Session 为锚，长期知识以 Agent Memory 为锚；协作事实以 Server 为权威，Memory 正文以 Agent Home 为权威。**

## 五层上下文

### 第一层：Server 协作事实

PostgreSQL 中的 Space、Member、Channel、Thread、Message、Task、Inbox Item 和 Run 是协作事实。它们回答“谁能看见什么、谁被要求做什么、工作处于什么状态”。Computer 的缓存不能替代这些事实。

主要约束包括：

- Human 和 Agent 共用 Member、Space、Channel、DM、Thread、Message 模型；
- 一个 Run 只有一个 Focus Thread；绑定 Task 时 Focus 必须是该 Task 的 Linked Thread；
- 一个 Agent 同时最多一个 active Run；
- 一个 Task 只能从 Root Message 建立一个不可更换的 Source Thread；
- 所有领域写入在一个事务入口中完成。

### 第二层：一次 Run 的快照

Server dispatch Run 的事务在刷新 `RunDispatched` effect 时构造并持久化 `run.start` command；该 command 冻结以下事实，再投递给 Computer：

- Agent identity、Role 和 Role revision；
- 可选 Task 的 id、短序号、title、status、Source/Linked Thread；
- 唯一 `focus_thread_id`；
- Focus Thread 的 Root 和 replies，以及该 Thread 的最新 `message_snapshot_sequence`；
- Focus 所属 Channel 的 `channel_snapshot_sequence`；
- 本次已分配的 Inbox Items；
- Focus Channel 的当前成员列表。

`channel_snapshot_sequence` 来自 Channel 的 `next_seq - 1`，所以它包含 Root、reply、Action Message 和 System Notice 的共同序号空间。它是读取上限，不是主时间线行号。

### 第三层：Channel 活动增量

完整 Channel 不会每次都复制进 Prompt。Computer 在本地 SQLite 为每个 `(Agent, Channel)` 保存 `through_sequence`：

1. RunStart 冻结上限 `channel_snapshot_sequence`。
2. Computer 通过独立 query 请求 Server 读取 `(through_sequence, snapshot_sequence]`，分页上限为 256。
3. Computer 排除当前 Focus Thread 的消息和已作为 Hard Item 交付的消息，形成 `channel_activity`。
4. 只有 Completed 或 Yielded Run 才把 cursor 推进到该快照；Failed/Canceled 保留旧 cursor，下一次可重读。

这是一种可重建的活动投影，不是第二份消息事实。投影丢失时可以从 Server 的可见范围重建。

### 第四层：Provider Session

Computer 按 `(Agent, scope, generation)` 保存 Provider Session：

- 无 Task 时 scope 通常是 `Thread(focus_thread_id)`；
- 有 Task 时 scope 是 `Task(task_id)`，可跨多个 Linked Thread；
- fingerprint 包含 Driver、workspace fingerprint、Role revision，以及排序后的 Linked Thread ID 的 SHA-256。字段名是 `audience`，但当前实现没有把成员集合纳入该 hash。

只有 Session 为 Ready 且 fingerprint 相同才 Resume。以下变化会新建 generation：

- Task 结束；
- Linked Thread ID 集合改变；
- Driver、Role 或 workspace 改变；
- locator 丢失或 resume 失败；
- 显式 reset。

单独的 token 阈值、Run 次数、固定时间、Server/daemon 重启或 Yield 不会自动成为换代理由。重启后若本地 transcript 和 locator 仍可恢复，Session 可以继续；恢复失败则新建 generation，并从 Server 事实、Memory 和结构化 Run 结果重建。

产品设计还要求“Linked Thread 成员集合不兼容”时更换 generation。当前 fingerprint 不能识别“同一批 Thread、成员变更”的情况，不能把这一条讲成现有代码保证；详见 [实现与设计核查](./08-实现与设计核查.md)。

### 第五层：Memory 和 workspace

Memory 是 Agent 的跨 Run、跨 Channel 知识：

- Product Contract 要求每个 Run 在实质工作前读取 `memory/MEMORY.md`；运行时不会自动把正文注入 Prompt，也不会强制调用读取；
- 详细内容放 `memory/notes/`；
- Product Contract 还要求影响后续协作的学习在相关回复、Item disposition 或 yield 前写回；
- Product Contract 禁止把 Message 历史或 Provider transcript 原样复制进 Memory；
- Computer 在启动 Run 时本地列出文件名、大小、SHA-256、更新时间，放进本地 `RunInput`；Server 不持久化这些元数据或正文，只能在 Agent 在线时经 query 读取投影或正文。

本地 `RunInput` 中的 `memory` 是文件索引元数据。模型可通过 Agent CLI 的 Memory read 读取正文；Builtin 也可通过受限 `read` 工具读取 `memory/MEMORY.md` 或 Memory 相对路径。workspace 文件同样经受限工具读取。

## 模型看到的上下文并不等于 Run 快照

`RunInput` 先保存完整执行输入，再由 `model_view()` 生成模型视图：

- Focus Root 永远保留；
- replies 默认只保留最近 5 条；
- 更早 replies 标出省略数量，模型按需调用 `thread.read`；
- Item 若引用的 Message 已在窗口中，只传 Item 身份，避免重复正文；窗口外的 Item 才携带内容；
- 去掉内部同步字段，只保留模型需要的 identity、work、run_context、成员和引用标识。

这体现了一个重要取舍：**一致性字段留在运行时，模型只收到足够完成工作的投影。**

## 上下文压缩

通用 `sumi-agent-core` 只定义 `ContextStrategy` 接口，不拥有 Sumi Prompt 或压缩规则；`sumi-builtin-agent` 实现 Builtin 策略。

Builtin 的流程是：

1. 根据最近一次 provider 上报的 input tokens，加上之后追加消息的字符估算；没有 usage 才全部使用 chars/4 估算。
2. 达到配置的 trigger，或 provider 明确返回 context-limit 错误时，选择保留最近 `keep_recent_tokens` 的尾部。
3. 切点只落在 user/assistant 消息，不能切断 tool result；若切在一个 turn 中间，额外摘要被压缩的 turn 前缀。
4. 摘要后附加被压缩区间的文件读取/修改清单，避免文件事实丢失。
5. 把 `through`、summary 和 compaction record 存入 Provider Session metadata；下一次投影是“摘要 + 未压缩尾部”。
6. provider context-limit 重试前比较压缩前后的 projected context；如果没有实际改变，不重复发送同一个超限请求。

稳定的 Product/Driver Contract 每个 turn 都重新加入，因此压缩不会成为保留产品规则的唯一手段。

## 一次 Run 的上下文时序

```text
Server 选 Focus + Task + Items + channel_snapshot
        │
        ▼
Computer 读取 Memory 索引、workspace fingerprint、channel through cursor
        │
        ▼
组装 RunInput（完整运行输入）
        │
        ├─ model_view：Root + 最近 replies + 活动投影
        └─ session scope/fingerprint：决定 Resume 或新 generation
        │
        ▼
Provider Session 投影（必要时压缩）→ 模型 turn
        │
        ▼
CLI 写入领域事实；Run 完成后推进成功的 channel cursor
```

## 能保证什么

- Run 不会因为模型只看到最近 5 条消息而失去读取历史的能力；历史有明确 CLI 入口。
- 同一个 Agent/Task scope 的兼容 Session 可以跨 Run 复用；Session 丢失不删除 Task、Message、Result 或 Inbox。
- 失败 Run 不推进普通 Channel 活动 cursor，避免因失败而永久漏读。
- Focus、Task、Channel 和 Item 的关系在 Server 和 Computer 两侧都做 scope 校验。

## 不能保证什么

- Focus 默认不是整个 Space，也不是所有 Linked Thread 的全文；关联 Thread 需要按需读取或通过 Task 上下文获取。
- 如果协作者把同一讨论拆到多个 Root/Thread，Agent 可能只先看到各自 Focus；系统没有“游戏回合”这一额外领域概念。
- Provider Session 是缓存，不是事实库；Provider 自己丢失 transcript 时只能冷启动重建。
- Prompt 压缩和 Memory 写入不能保证模型一定正确总结，必须用持久事实和测试验收。
