# 01 讲解总览：Sumi 的设计主线

## 结论

Sumi 的核心设计是“事实、注意力、执行、连续性分层”。Server 维护谁在什么 Space、Channel、Thread 中说了什么、哪个 Task 处于什么状态、哪个 Agent 有待处理事项；Computer 只执行 Server 已经授权的 Run，并保存本机的 Memory、workspace 和 Provider Session；模型只能经 Driver 提供的受限工具和 Agent CLI 请求领域动作。

这条边界让模型的偶然输出不会直接成为系统事实，也让模型会话丢失不等于协作记录丢失。

## 组件边界

```text
Human / Browser
       │ HTTP、SSE
       ▼
Server（PostgreSQL + 领域事务 + outbox）
       │ versioned WebSocket command/query
       ▼
Computer（本地 SQLite + Agent Home + recovery）
       │ Run / Session
       ▼
Driver（Builtin 或 Codex）
       │ provider API / app-server
       ▼
模型
       │ 只能调用受限工具和 Agent CLI
       └──────────────► Server 的结构化 Action
```

### Server

Server 是协作事实的唯一权威，保存 Space、Member、Channel、Thread、Message、Attachment、Task、Inbox Item、Run 和审计/outbox。它执行成员关系、可见性、Task 关系、Run 归属和状态转换，不执行模型，也不保存 Provider Session、Memory、workspace 或模型凭据。

### Computer

Computer 与一个 Space 配对，承载多个 Agent。它保存每个 Agent 的 Agent Home、Memory、workspace、Driver 私有状态、Provider Session、本地命令和结果 outbox。它把 Server 的 Run 快照转换成 Driver 调用，并在重启后依据本地事实和进程证据恢复。

### Driver

Driver 是模型供应商适配层。Builtin 使用 OpenAI-compatible chat stream；Codex 使用 app-server。Driver 负责会话打开/恢复、turn、steer、interrupt 和完成通知，但不决定 Task 是否完成，也不能绕过 Server 写 Message、Result 等协作事实；Memory 留在 Agent Home，经本地受限工具或 Memory CLI 读写。

### Agent CLI

Agent CLI 是当前 Run 内唯一的 Sumi 写入口。Agent、Space、Task、Focus、Run 从 Driver token 和本地 capability 推导，Agent 不需要重复提交这些身份。CLI 请求经过 Server 的权限、关系、快照和幂等检查。

## 一条完整链路

以 Human 在 Channel 发布一条要求为例：

1. Server 在一次事务中写入 Message，并把 mention、reply、DM 或 Task Activity 转成结构化 Hard Inbox Item。
2. Server 找到没有 active Run 的 Agent，创建 Run，分配 Focus Thread 和待处理 Item，再把 `run.start` 写入 Computer command outbox。
3. Computer 持久化命令，读取 RunStart 快照，补齐频道增量上下文，解析 Session scope 和 fingerprint。
4. Driver 以合适的 Provider Session 发起 turn。模型若要回复、确认 Item 或建 Task，必须调用 Agent CLI；读取 Memory 可使用 CLI，Builtin 也提供受限 `read` 工具。
5. CLI 请求回到 Server 的单一领域事务入口。事务同时更新 Message/Task/Inbox/Run 关系并写 outbox；Computer 只收到结构化结果。
6. Computer 在所有 Item 有 disposition 后提交 Run result。Server 最终决定 Task、Inbox 和公开 Result 的状态。

可用一条诊断链复盘全过程：

```text
message_id
  → inbox_item_id
  → task_id（如有）
  → run_id
  → command_id / computer_seq
  → delivery_seq / outcome
  → disposition
  → result event / Result Message
```

## 五个设计原则

### 1. 持久身份先于模型会话

Agent 身份、Role、Message、Task、Result、Memory 的生命周期独立于某一次 Run、Provider Session 或 Computer 进程。Provider Session 只是效率和连续性缓存。

### 2. 结构化事实先于正文猜测

路由最终读取 `message_mentions`、reply 父子关系、Task link、Thread subscription 和 Item strength。Agent CLI 发送的显式 `@display_name` 会在唯一写入入口按当前 Channel 成员解析并归一化为 `message_mentions`；后续消费者不再猜 Markdown。普通自然语言中的“请某人处理”不改变身份、权限或 Task/Run 归属。正文、附件、网页和工具输出都按不可信输入处理。

### 3. Server 做授权，模型做决策

Prompt 可以告诉模型怎样使用工具，但不授予权限。Server 负责检查 Space、Channel、Task、Run 和 Member 关系；Computer 负责 capability，Builtin 还以本地沙箱限制工具。Codex 当前没有同等的 OS 隔离，见 [提示词优化与安全](./04-提示词优化与安全.md)。

### 4. 每个事实只有一个写入口

Browser 和 Agent CLI 共用同一组 application/domain 事务。Message、Task 终态、Inbox disposition、Run result 不允许两套互相漂移的实现。

### 5. 失败要可恢复且可解释

命令、结果、delivery receipt、Run result 和 HTTP 写入使用稳定 ID/幂等键；断线不直接判定 Run 失败；只有 Computer 观察到 Driver 丢失或重启等证据时才收尾。

## 适合开场的讲解顺序

建议先画“Server—Computer—Driver—模型”四层，再用一条 Message 链路串起以下问题：

- Run 的执行锚点是哪个 Thread；Task 和 Provider Session 为什么是另外两种锚点；
- `channel_seq`、`delivery_seq`、Builtin mailbox FIFO 各自保证什么；
- Prompt 如何分成稳定合同和动态数据；
- 哪些规则由 Server/沙箱强制，哪些只能作为模型行为建议；
- 断线、重复命令、旧 Session、未处理 Item 如何被恢复和审计。
