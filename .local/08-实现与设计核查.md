# 08 实现与设计核查：讲解时的准确口径

## 用法

`docs/DESIGN.md` 和 `docs/SYSTEM_DESIGN.md` 定义产品与系统要求；本文件记录本次按当前代码、schema 和测试核对后，不能直接把“要求”说成“当前已强制实现”的地方。

讲解时可使用三种明确表述：

- “当前代码保证”：有对应入口、约束或测试。
- “产品要求”：设计已经定义，后续实现必须满足。
- “当前缺口”：代码尚未完全落实，不能作为安全或一致性承诺。

| 主题 | 当前结论 | 讲解时的短句 |
| --- | --- | --- |
| Agent mention | Agent CLI 的显式 `@display_name` 会在写入入口解析一次并存为 relation。 | “后续路由不猜正文；但写入时有受定义的 mention 语法。” |
| Session audience | 当前 hash 是 Linked Thread ID 集合，不是成员集合。 | “同 Thread 成员变更目前不保证重建 Session。” |
| `delivery_seq` | 正常路径连续，Computer 严格验序；Server rehydrate 不单独验缺号。 | “连续性主要由分配路径和 Computer 守住，不是数据库无缺号约束。” |
| Memory | Contract 要求先读，运行时不自动读正文。 | “这是模型应做的动作，不是 runtime 已替它做完。” |
| Human redirect | 调度器预留优先级，当前 RunStart 固定为 `false`。 | “不能把它演示成已有的 Human 插队流程。” |
| Harness `/tmp` | 只有 Builtin 有真实统计。 | “不能拿这一列比较 Builtin 与 Codex 的安全性。” |
| Codex isolation | 以 `dangerFullAccess` 运行。 | “Server 校验仍有效，但本机 OS 隔离不能与 Builtin 等同。” |

## 1. Agent 消息中的 mention 不是“完全不解析正文”

### 当前代码

`src/server/adapters/http/execution.rs` 的 `agent_mention_ids()` 从 Agent CLI 发送的 Markdown 扫描显式 `@display_name`。它只在当前 Channel 成员中匹配，再把结果传给唯一的 Message 写入入口，落为 `message_mentions`。

`src/server/adapters/postgres/conversation.rs` 的后续路由读取 relation，Inbox、图谱和其它消费者不会再次从持久 Markdown 推断收件人。

### 准确解释

下面两句话可以同时成立：

- Agent CLI 的 `@display_name` 是受定义的写入语法，能够产生 mention 路由。
- 任意自然语言指令不能改变 Agent、Space、Task、Focus、Run 身份或权限；持久化之后，消费者只读结构化 relation。

不要说“Server 从不解析正文”。也不要把“请某人处理”与显式 `@display_name` 混为一谈。

### 影响

这不是把权限交给正文。解析的结果仍受 Channel 成员范围限制，并在同一写入事务内变为受 Server 校验的关系；权限判断不依赖模型文本。

## 2. Provider Session 的 `audience` 指纹尚未覆盖成员变化

### 当前代码

`src/computer/adapters/server_connection.rs::session_fingerprint()` 对排序后的 Linked Thread ID 做 SHA-256，把结果写进 `SessionFingerprint.audience`。它同时包含 Driver、workspace fingerprint 和 Role revision。

因此，以下变化会使 fingerprint 不同并创建新 generation：Driver、workspace、Role revision 或 Linked Thread ID 集合变化。Task 结束也会由 Server 发出 `session.close`。

同一组 Linked Thread 内的成员增加、移除或替换，不会改变当前 hash。`SessionChangeReason::AudienceChanged` 目前只有协议枚举，当前执行路径没有产生该原因。

### 与设计要求的差异

系统设计要求 Linked Thread 成员集合不兼容时更换 generation。当前实现不能检测“Thread ID 不变、成员集合改变”，所以不能承诺这种成员变更一定使旧 Provider Session 失效。

### 仍然有效的边界

Server 在新的读取和写入时仍执行 Channel membership、Task/Thread 关系和权限校验。因此 Session 未重建不等于成员变化后能越权读写；风险是旧 transcript 的连续性不应被描述为已按成员变化隔离。

## 3. `delivery_seq` 的连续性有两道不完全相同的检查

### 当前代码

`DispatchRun` 创建初始 Run Items 时按 1、2、3… 分配；`Run::attach()` 也从最后一个 sequence 加一。`run_items` 有 `(run_id, delivery_seq)` 唯一约束，并要求 sequence 大于 0。

Computer 的 `LocalRun::rehydrate()` 和 `LocalRun::attach()` 严格拒绝缺号、重复和 scope 错配。Server 的 `Run::rehydrate()` 则只拒绝 0、重复 Item ID 与重复 sequence，没有显式拒绝 `1, 3` 这种缺号快照。

### 准确解释

可以说“正常投递路径连续，Computer 会拒绝不连续交付”。不要说“Server 数据库和 Server domain 都独立证明每个 Run 永远没有缺号”。

这不影响 1/2/3 的因果解释：顺序主要来自 Message 提交后才创建下游 Item、单 Agent 单 active Run 和本地连续 delivery；它不是一个全局回复排序器。

## 4. `channel_seq` 与 System Notice 的展示语义

### 当前代码

`src/server/adapters/postgres/conversation.rs` 以 `UPDATE channels SET next_seq=next_seq+1 RETURNING next_seq-1` 分配 Channel 坐标。reply 和 Action Message 可以占用 sequence，但主时间线不展示 reply。

System Notice 当前写为 `placement='root'`，UI 将其作为系统行展示，并可折叠同日连续 Notice。它不是“被 seq 占用却从主列表消失”的消息。

### 准确解释

`channel_seq` 是引用和快照上限，不是 UI 行号或发言轮次。主列表的跳号通常来自 reply 或 Action Message；System Notice 仍是可见的 root 系统行，只可能因 UI 折叠而不逐条展开。

## 5. Memory 的“必须读取”是合同，不是自动注入

### 当前代码

`crates/sumi-builtin-agent/src/prompt.rs` 的 Product Contract 要求 Agent 在每个 Run 的实质工作前读取 `MEMORY.md`。但 `src/computer/adapters/server_connection.rs` 只在 Computer 本地枚举 Memory 文件元数据，放入本地 `RunInput`；它不会把 `MEMORY.md` 正文自动塞进模型上下文，也不强制模型发起读取。

Builtin 可以经受限 `read` 工具读取 `memory/MEMORY.md`，也可以使用 `sumi agent memory read MEMORY.md --json`。不能说“只能通过 CLI 读取”。

当前 `RunStart` command 和 Server schema 不持久化 Memory metadata 或正文；需要时可经在线 Computer query 读取投影或内容。Memory 的权威副本在 Agent Home。

### 准确解释

可以说“Memory 是跨 Run 的本地恢复入口，Prompt 明确要求先读，工具提供读取路径”。不能说“系统已保证每次读取”或“模型已经看到了 Memory 正文”。

## 6. Scheduler 已有 Human redirect 字段，但当前没有业务写入路径

### 当前代码

`src/computer/core/scheduler.rs` 的优先级顺序预留了 `explicit_human_redirect`，其后是 Hard/Ambient、`available_at` 和 Task continuity。

`src/computer/adapters/server_connection.rs` 在处理 `RunStart` 时固定构造 `explicit_human_redirect: false`。Server 的候选查询目前按每 Agent 一个候选、Hard 优先、available time、Task continuity 选择。

### 准确解释

可以介绍这是一项调度扩展点。当前演示只应讲容量、单 Agent 单 slot、round-robin 与上述实际优先级；不要把“Human 显式重定向优先”说成已有产品流程。

## 7. Live harness 的指标有 Driver 覆盖范围差异

### 当前代码

`tests/builtin_harness_benchmark.rs` 从 Builtin Provider Session 读取 usage 与 compaction records；Codex 从 app-server 生成的 rollout JSONL 读取 token 和 `compacted` 事件。

`count_tmp_attempts()` 只扫描 Computer 日志中同时包含 `Builtin tool failed` 和 `/tmp` 的行。该函数仅在 Builtin metrics 路径调用，Codex `DriverReport` 没有等价采集，因此保持默认 0。

### 准确解释

可横向比较同脚本下的完成、token、缓存、压缩、probe 和台账结果，但仍要说明 Provider live run 有波动。`/tmp attempts` 只能作为 Builtin sandbox/tool 行为的诊断，不是 Codex 比较基准。

## 8. Codex Driver 的安全与注入边界

### 当前代码

`src/computer/drivers/runtime.rs` 为每个 Agent 常驻一个 Codex app-server。启动命令含 `--dangerously-bypass-approvals-and-sandbox`，每个 `turn/start` 也传 `sandboxPolicy.type = dangerFullAccess`。`turn/steer` 的 Remote error 会映射为 `TooLate`；`notice()` 当前是 no-op。

当前 Agent 的 Driver token 会注入该 Agent 的 app-server 环境，并由其工具子进程继承。它能代表当前 Agent 调用 capability，但不能成为其他 Agent、Browser Session 或 Computer Token。

### 准确解释

Server 的身份、成员关系、资源关系与幂等校验仍是强制边界；Message 里的提示注入也不会授予 Server 权限。可是 Agent Home、进程划分和 capability 不能替代 Builtin 的 `sandbox-exec`/`bwrap` OS 隔离。不要以“每 Agent 一个 Home”推导出 Codex 已有文件或进程级隔离。

对运行中的 Hard Item，Codex 可通过 `turn/steer` 接收 Accepted/TooLate outcome；普通 notice 目前不会注入正在执行的 Codex turn。这是 Driver 能力差异，不应被 FIFO mailbox 的 Builtin 语义掩盖。

## 9. RunStart 快照在 Server 的 dispatch 事务中构造

### 当前代码

`DispatchRun` 发出 `Effect::RunDispatched`。Postgres transaction 的 `flush_effects()` 调用 `effect_record()`；后者在同一事务中调用 `run_start()` 读取 Focus、Task、Items、Channel snapshot 和成员，再把完整 `run.start` command 写入 `computer_commands` 与 outbox。

### 准确解释

不要说“Server 收到 `run.start` 后冻结快照”。方向相反：Server 在 dispatch 时构造并持久化 command，Computer 收到命令后基于该快照建立本地 RunInput，并补齐本机 Memory 元数据和 Channel 增量。

## 10. 演示前的最小核对清单

- 用结构化因果链演示 A → B → C；不要同时独立触发三个 Agent 后宣称有全局顺序。
- 展示 `channel_seq` 时同时打开 Thread，说明 root、reply、Action Message 与 System Notice 的 placement。
- 把 Prompt 结果展示为持久事实、CLI error code、Run/Item disposition 和 harness artifact，不展示模型自述作为验收证据。
- 明确标记 Builtin 与 Codex 的差异，尤其是 Memory 自动读取、notice 注入、`/tmp` 指标和 OS sandbox。
- 对成员变更后的 Task Session，不宣称当前代码一定重建 generation；如需该安全性质，应先补充 fingerprint 与回归测试。
