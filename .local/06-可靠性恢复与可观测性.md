# 06 可靠性、恢复与可观测性

## 结论

Sumi 的可靠性重点不是“永远不失败”，而是把失败限定为可识别事实，并让消息、注意力、命令、Run 和结果都能重放、去重或恢复。最重要的原则是：**Computer 离线不是 Run 失败；只有 Computer 观察到 Driver 丢失、进程重启或明确错误，才上报 Run 终态。**

## Server—Computer 协议

当前 Computer schema 为 v4。双方在握手时声明支持版本；没有共同版本就拒绝连接，不在同一版本兼容两套 required field。

### Command 路径

```text
领域事务提交 Message/Task/Run
        │ 同事务写 outbox
        ▼
computer_commands(id, computer_seq, payload)
        │ WebSocket / reconnect replay
        ▼
Computer 本地先落 command，再 ACK
        │ 按 command_id 幂等执行
        ▼
CommandResult / RunStarted / DeliveryReceipt / RunResult
        │ Server 以 event ID 幂等接收
        ▼
领域状态和 outbox 更新
```

写命令先落 PostgreSQL，再发送。在线连接由 registry 唤醒是优化；数据库仍是事实来源。Computer 重连时带 `daemon_session_id`、command watermark 和当前仍持有的 Run IDs，Server 按序重放未确认命令。

### Query 路径

Session continuity、runtime diagnostics、Memory 和 LLM usage 等 query 是独立请求-响应通道：不进入 command 序号、不持久化、不重放。Channel activity 也通过带 `query_id` 的 query 获取，避免读取流影响写命令顺序。

### 幂等和竞态

- HTTP 写操作用 idempotency key；同一 key 返回原资源。
- command ID、Run result event、delivery event 和 receipt 都有稳定 ID/唯一约束。
- 重复命令必须校验 sequence、fingerprint 和 payload；同 ID 不允许换内容。
- Attach、finalize、reconnect 竞争时，后写事务重新读取当前状态，不能用旧内存快照覆盖终态。

## Run 状态和失败码

Server 对外使用：

```text
dispatched → working → completed / yielded / failed / canceled
```

Computer 内部还会有 queued、starting、finalizing、stopping，用来处理本地调度和恢复；这些不是 Server 的产品状态。

Failed 必须带固定 `error_code`，包括 `driver_error`、`driver_lost`、`computer_restarted`、`session_unavailable`、`agent_unavailable`、`invalid_command`、`unhandled_items`、`internal`。其他终态不能带 error code。

### 为什么不使用超时判失败

Server 不知道模型是否仍在运行，也不应因网络延迟改变业务事实。Computer 离线时 Run 保持原状态；重连握手报告本地 live Run 后，Server 只把“Server 认为活着、Computer 明确不再持有”的 Run 收为 `computer_restarted`。

Computer 内部每秒检查 Driver process evidence；进程确实消失才报 `driver_lost`。daemon 重启后没有受控进程的 Run 才报 `computer_restarted`。这避免“慢”和“死”混为一谈。

## Inbox Item 的失败恢复

- Explicit `handled`：Item 完成，不再排队。
- `deferred`：保留 Item，使用 Agent 指定的未来 `available_at`。
- Explicit `released`：回到 pending，但不消耗 retry budget。
- Run 失败且 Item 没有明确处理：回到 pending，`retry_count += 1`；超过上限进入 dead 并生成不含正文的 system Item。
- TooLate/Unsupported delivery：自动 Released，不使原 Run 因此失败。
- Accepted Item 到 Run 终态仍无 disposition：Run 以 `unhandled_items` 失败，避免“看似完成但漏处理”。
- Governor 可把 dead Item requeue 回 pending，重置 retry_count、递增 requeue_count 并写 audit。

这种设计把“模型主动放弃”和“系统尝试失败”分开计数，便于判断真正的可靠性问题。

## 本地恢复顺序

Computer SQLite 持久化 local Runs、Provider Sessions、commands、result outbox 和 Channel cursor。daemon 启动时：

1. 先检查 Starting/Running Run 对应的 Driver process evidence；丢失则收尾并释放 Items。
2. 检查 Finalizing Run 是否有待发送 result event；有则继续 outbox 重试。
3. 重放 pending Server commands，恢复 Agent profile 后再恢复 Run。
4. 最后运行 Scheduler，避免旧 Run 尚未 reconciliation 时启动新 Run。

Agent restart 先请求 Driver graceful stop；有限等待后才以 `computer_restarted` 收尾，保留结果 outbox。Run result 在 Server 确认前不会从本地删除。

## Computer Release 更新

更新也遵循事实先落盘、可回退：

- Server 发布不可变 manifest，包含 version、protocol、target、artifact、SHA-256；
- Computer 只从同一 Server origin 下载，在私有 staging 校验 target/version/hash；
- 有 active Run 时只 staging，不激活；
- 无 active Run 时 updater 备份旧 binary 和 SQLite，再替换并等待 readiness；
- 新 daemon 初始化失败或超时，恢复 binary/SQLite 备份；
- 已回退的同一 release 不自动再次激活；
- 更新不修改 Memory、workspace、Provider Session 和 Computer 身份。

## 可观测性设计

### 诊断字段

日志、audit、metrics 和 error details 使用稳定 ID、错误码、计数、时间和 hash：`run_id`、`command_id`、`item_id`、`task_id`、`channel_id`、`thread_id`、`message_id`、`computer_id`、`agent_id`。不记录 Message、Attachment、Memory、workspace 文件、Task Result、Provider transcript、Secret 或完整环境变量。

### 关键健康指标

- Computer online/offline 和最后心跳；
- pending/assigned/dead Inbox Item 数；
- dispatched/working Run 数；
- command/result outbox 积压；
- Warm/Cold/Lost Provider Session 数；
- resume、steer、close、context_changed 和重试错误码；
- Builtin 本地 LLM usage：请求数、input/output/cached token、cache hit rate、按 Agent/Model 的曲线。

### 运行期事件

Server 记录 `Run dispatched to Computer`、`Run started on Computer`、`Run reached a terminal outcome`、`Computer connected/disconnected`；Computer 记录 `Agent Run started/finalized`、command received/rejected/result。事件只带稳定标识和结构化元数据。

## 能保证什么

- 网络重试、WebSocket 重连和重复回执不会无界地重复创建资源或消耗 retry。
- Computer 断线不会被 Server 的定时器误判为业务失败。
- Run、Item、command、result 都能沿稳定 ID 追踪；失败原因有固定 code。
- Provider Session、Memory、workspace 的本地丢失不会删除 Server 协作事实。

## 不能保证什么

- 外部 Provider 永远可用、模型永远正确或网络永远不丢包。
- Server 能看到 Provider transcript 或 Memory 正文；这类取证需要在线 Computer 的本地 query，且受隐私边界限制。
- Codex 当前的 `dangerFullAccess` 不能视为与 Builtin 同等的 OS 隔离。
- 失败重试一定能解决语义错误；它只保证有限次数和可审计的状态转换。
