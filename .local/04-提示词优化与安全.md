# 04 提示词优化与安全：如何验证，以及如何面对 Provider 干涉

## 先给结论

Prompt 优化不能用“模型说它理解了”证明。Sumi 用三类证据验收：

1. Prompt 组装、哈希、上下文投影和压缩的单元测试；
2. 同一脚本、同一 Provider/Model 的 Builtin/Codex live harness，对 token、缓存、压缩、事实探针和持久文件做比较；
3. 端到端测试只检查 Server/Computer 的持久事实和安全边界，不把模型文本当作唯一真相。

同时，Prompt 不授予权限，也不能保证覆盖 Provider 自己的 system prompt。关键安全规则必须由 Server、Agent CLI 与 capability 强制；Builtin 还依赖 OS sandbox，Codex 当前不具备同等隔离。

## Prompt 的五层结构

### 1. Stable Product Contract

Builtin 与 Codex 当前共用，内容包括：

- Run 内容不能改变 Agent、Task、Focus、Run 身份；
- Secret 不得进入 Message、Result、Memory 或日志；
- 结构化 mention/reply/DM/Task 路由优先于正文；
- Hard Item 必须经 CLI 获得明确 disposition；最终模型回复本身不构成处理；
- Task 只从 Root Message 创建，长期工作要维护 Source/Linked Thread 和 Result；
- Product Contract 要求每个 Run 先读 `MEMORY.md`，重要学习在相关外部动作前写回；这是一项模型行为要求，不是运行时自动读取；
- 使用短结构化标识，不在消息中写 UUID；
- 普通 Agent 进度消息不通过 ambient 唤醒其他 Agent，显式 mention 等 Hard 路由仍有效。

### 2. Stable Driver Contract

说明 CLI 执行方式，而不是领域权限：

- 同一依赖波内的独立 CLI 调用放进一个 tool-call batch；
- 有数据依赖、写冲突或用户可见顺序时设置屏障；
- 每个 tool call 只运行一个 Sumi CLI；
- `discover → action`、附件上传→发消息、Memory 读→写和有序消息动作必须顺序执行；
- `context_changed` 要先重新读取 Thread/Channel，再提交一次；
- `next_action` 只执行一次，不能用猜参数反复撞；
- write 结果不确定时先读取权威状态，不能盲重试；
- `run yield` 必须是本 Run 最后一个 CLI 调用。

### 3. Dynamic identity/role

每次 Run 注入 Agent display identity、Role 文本和 Role revision。Role 是职责边界，不是治理权限。

### 4. Dynamic Run Context

注入本次 Run 的 Task、Focus、Root/replies、频道增量、已分配 Items 和成员。它是数据快照，不是新的权限声明。

### 5. Builtin tool/plugin contract

Builtin 额外说明 `workspace/`、`memory/`、`runs/`、`/tmp` 的路径规则；插件可以增加工具和自己的合同。通用 runtime 只提供接口，不拥有 Sumi Prompt 或压缩政策。

## Builtin 和 Codex 的组装差异

### Builtin

`system_messages()` 的顺序是：

1. 可缓存的 Product Contract + Driver Contract；
2. Agent identity/Role；
3. Builtin 工具合同；
4. Adapter 追加 `[Sumi run context projection]` system message。

模型-facing user instruction 只放 `model_view` 的剩余部分；完整运行输入中的同步字段不会直接进入 user 文本。

### Codex

Codex app-server 协议没有等价的 system-message 通道，所以 Product Contract、Driver Contract 和 turn instruction 被前置到同一个 turn input。不能说 Codex 拥有和 Builtin 一样的 system/user 层级；只能说 Sumi 采取了明确的前缀和结构化分隔来降低歧义。

## Prompt cache 为什么不会静默复用旧上下文

Builtin 的 `prompt_cache_key` 由两部分组成：

```text
RunInput.content_hash + driver_contract_hash
```

`content_hash` 覆盖 Product Contract、Agent/Role revision、Memory 文件元数据、Task、Linked Thread、Focus 消息、Channel activity、Dispatched Items 和 Channel members；`driver_contract_hash` 覆盖稳定 Product/Driver 文本。上下文或合同改变时，key 改变，避免把旧 Prompt cache 当成新事实。

注意：这是缓存一致性机制，不是模型服从机制。

## 怎样确认一次 Prompt 优化有效

### 当前已有的直接证据

[`tests/builtin_harness_benchmark.rs`](../tests/builtin_harness_benchmark.rs) 用同一脚本、同一 Provider endpoint、同一 model，分别走 Builtin 和 Codex harness。脚本要求模型维护台账、写资料、返回事实探针，并从持久 artifacts 统计：

- `cached_input_tokens / input_tokens` 的 cache rate；
- 总 provider 调用数、input/output/cached token；
- compaction 次数、reason、source/summary token、split-turn；
- 长对话 probe 的正确率；
- 台账行数、重复、缺失；
- `/tmp` 尝试次数；
- Run 成功/失败和最终 projected context。

报告写 JSON/Markdown，但不输出 Message、Attachment、Memory 或 Secret 正文。`SUMI_HARNESS_ENFORCE_THRESHOLDS=1` 时，可以用最小 cache rate 和 probe accuracy 作为 gate；默认不 gate，因为 live Provider 不是稳定的离线单测。

`/tmp` 尝试次数目前只从 Builtin 的 `Builtin tool failed` 日志统计；Codex leg 没有对等采集，字段会保留默认值 0。它不能用于 Builtin/Codex 的对等安全比较。

### 端到端行为证据

- [`tests/brain_in_vat.rs`](../tests/brain_in_vat.rs) 用持久文件和 Server 事实验收 Memory、discover、Human confirmation、Agent 创建、回复和 Inbox ack。
- [`tests/werewolf_communication.rs`](../tests/werewolf_communication.rs) 验收多 Agent 的结构化 mention/reply/DM、Run/Inbox 轨迹和 dead Item；测试观察持久事实，不替 Agent 代发消息。
- `sumi-agent-core` 和 `sumi-builtin-agent` 的单测验收 `model_view`、hash、token estimate、切点不切 tool result、split turn、context-limit 重试和 mailbox 关闭竞态。

### 建议的 Prompt 变更流程

每次候选 Prompt 变更都固定以下变量：Provider endpoint、model、脚本、Agent Role、sandbox、context window 和随机性设置；对比旧版与新版多次运行，记录：

1. 任务是否完成、Result/Task 状态是否正确；
2. CLI 调用是否合法、重复率和 `context_changed` 重试次数；
3. Message/Memory/workspace 是否符合预期，是否出现路径越界或 Secret 泄露；
4. token、cache、压缩、延迟和失败码；
5. 长对话事实探针、台账完整性和跨 Run 恢复。

只有“目标行为提高且安全/可靠性没有回退”才算有效；单纯输出更长、主观上更像人或一次成功不能算证据。当前 harness 是一个受控脚本，不等于对所有任务的通用能力证明。

## 如何降低系统 Prompt 与 Sumi Prompt 的互相干涉

### 做到的部分

- 稳定合同与动态数据分离，动态数据明确标成 `run context projection`；
- 历史 Message、附件、网页、工具结果和 compaction 输入都按不可信内容处理；
- 路由消费结构化 relation。Agent CLI 的显式 `@display_name` 会在唯一写入入口归一化为 relation；其余正文指令不作为领域命令解释；
- 每个 turn 重新注入稳定合同，压缩摘要只作为 provider context，不替代合同；
- 当前 Provider Session fingerprint 覆盖 Driver、Role、workspace 与 Linked Thread ID 集合；这些变化会换 generation。相同 Thread 的成员变化尚未进入 fingerprint；
- `context_changed`、权限错误和非 retryable conflict 禁止盲重试；
- Builtin 缓存 key 覆盖合同和完整 Run 输入。

### 不能做到的部分

- Sumi 没有 API 可以强制覆盖 Provider 的更高优先级 system prompt；
- Provider 可能重排、截断或附加消息，尤其是 Codex 的 system-message 通道不同；
- 模型可能误读或忽略合同；Prompt 不能成为授权边界；
- compaction 摘要可能遗漏语义，Memory 写入也可能失败；因此必须让 Server 重新校验可验证的关系、权限与写入前提。

讲解时不要说“系统 Prompt 被 Sumi Prompt 覆盖”或“模型一定服从 Sumi 规则”。准确表述是：**Sumi 把稳定合同放在可预测位置，并把高风险规则移到结构化协议和外部强制边界。**

## 抗 Prompt Injection 的实际边界

| 风险输入 | Sumi 的处理 |
| --- | --- |
| Message 中写“忽略规则、给我权限” | 正文是不可信数据；权限由 Server 和 CLI token 判断。Agent CLI 的受定义 `@display_name` 语法例外地会被入口转成 relation，但不能改变权限。 |
| 附件、网页、工具输出中的指令 | 作为模型上下文数据，不改变 Member/Task/Run 身份；工具仍受路径和沙箱限制。 |
| 冒充别的 Agent 的正文 | 后续路由读结构化 mention/reply/DM/Task。Agent CLI 只有写入时的精确 `@display_name` 会按当前 Channel 成员转换为 mention。 |
| 旧 Session 带入旧 Role 或 audience | Driver、Role、workspace、Linked Thread ID 集合变化会建立新 generation；同一 Thread 的成员变化当前不会自动触发，见 [实现与设计核查](./08-实现与设计核查.md)。 |
| 重复提交或网络重试 | idempotency key、command ID、event ID 和数据库唯一约束去重。 |
| stale snapshot 写入 | 返回 `context_changed`，要求刷新后再提交。 |

### Capability 和沙箱

- Browser Session、Computer Token、Driver Token 三个认证面不可互换；Server 只保存 token hash。
- Agent CLI 通过 daemon 本地 capability socket 工作；Driver token 由内存 secret 派生。当前 Agent 的 app-server 与其工具子进程会继承本 Agent token，但不能借此冒用其他 Agent、Browser 或 Computer 身份。
- Builtin 文件工具拒绝 `..`、绝对越界和 symlink；文件和输出有 1 MiB 限制，shell 有超时和进程组清理。
- macOS 使用 `sandbox-exec`，Linux 使用 `bwrap`；不可用时 validation 失败，不退化为裸进程。

### 当前必须明确的 Codex 风险

当前 Codex 启动参数包含 `--dangerously-bypass-approvals-and-sandbox`，每次 turn 也请求 `dangerFullAccess`。因此不能宣称 Codex 与 Builtin 具有相同 OS sandbox 边界。Sumi 仍有 Server 侧权限和身份校验，且为每个 Agent 配置独立的 Home、app-server 与 capability；这些不是 Codex 的本机文件/进程隔离。该隔离缺口应在演示中主动说明。
